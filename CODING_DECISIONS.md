## 2. Ground truth

- **DECIDED 2026-10-11 (Tyler): no calibration, test or label on the September data from here on.** The four 2026-09-19 vault runs and every label made on them (Opus full labels, v3 / v4 / v5 relabels, v0.2 consistency and premise rounds) were made on pre-contract prompts (brand-free retention cells, pre-A3, pre-stage-contract seeds) and are not to be used to calibrate anything further. Every new test, reference sample and coder calibration draws from the first runs of the five contract-era trackers (AmEx 00dab505, Jira 182ef571, Pixel ce6df829, Netflix 1948d2ed, Doritos 2a0ff686 - vaulted 2026-10-11). Consequence for sequencing: the premise-in-coder vs prompted test, the keep-or-leave stance-field test and the criteria reason-bar test all need reference labels on the new data first, so the first labeling batch on the new runs should be drawn to serve those tests and the settled-customer sample together.


- **Provenance (fact, corrected 2026-09-21 and 2026-09-27).** No human-coded truth exists. The codebook and the 339 anchor labels (`jira/precedents_339.jsonl`) were written by Claude Fable 5 subagents in a Fable 5 session (2026-09-19); Tyler reviewed ~20. Claude Opus 5 subagents then labeled all 18,790 answers of jira / AmEx / Netflix / Pixel in-session (2026-09-20), ~88 answers per agent, told to follow the 339 wherever their judgment conflicted. Where a test answer was itself one of the 339, Opus copied Fable's label - the "100% agreement" with the reference set is copying, not independent confirmation. Never call these human labels.
- **Opus is the reference labeler (DECIDED 2026-09-20, Tyler).** Chosen to scale Fable's codebook to full sets (full ground truth, a second reference, training-scale labels) - not picked in a bakeoff. Grok 4 at full reasoning would cost about the same and was never measured; Grok 4 Fast is ~15x cheaper but scores outcome 68-79% against Opus, so it is not a truth candidate.
- **Division of labor (DECIDED 2026-09-22):** grok for discovery coding (open coding, brands pass); Opus for ratified-truth labels.
- **Run-to-run ceiling (measured 2026-09-27):** Opus 5.5 labeling the same answers twice agrees outcome 95%, top pick 92%, framing 98%, reasons Jaccard 0.83, brands Jaccard 0.90 (`labeling/v02_relabel/batching_test/`). Read every labeler-agreement number against it.
- **One answer per request (DECIDED 2026-09-27).** Batching 20 per request made labels less decisive (12 vs 7 one-sided changes), reasoned ~12% less and silently dropped 3 of 200 answers. The old labels' in-session batching explains ~5 points of their gap to new labels. On the API batching saves only ~2% (the codebook is cached). In-session labeling is fine when it is one answer per agent call (AmEx 500-answer test matched the API at the rerun baseline).
- **Precedents excluded from v0.2 (DECIDED 2026-09-27, Tyler).** Adding the 339 (judgment-only) moved Opus 5.5 labels 5-6 points toward the old labels - circular, since the old labels were made with them. Tyler's blind review of the 30 disagreements: plain v0.2 right 9, precedents right 6, both 15; outcome disagreements 9-5 for plain v0.2 (`source_test/blind_votes.json`, artifact claude.ai/artifact/RyUZnCuaKKoBVX7zjJi6vv).
- **One labeling standard per coder version (DECIDED 2026-09-27).** Every label in a version's training data comes from the same labeler, prompt and settings, with provenance recorded; a changed standard means relabeling, not mixing (a directional labeler shift baked into training shows up as fake trends). A fixed, ideally human-reviewed anchor set should vet any new labeler before it labels.
- **The pilot mints the anchor set (DECIDED 2026-10-12, Tyler).** The pilot's blind-review rows plus a slice of undisputed ones are promoted into a named file, with Tyler's votes on the disputed rows recorded as the truth - the first human-reviewed set under the new contract, and what vets the next labeler (an Opus successor, a prompted judge) before it labels anything.

## 3. Codebook contract

- **Reasons are brand-agnostic (DECIDED 2026-09-21, Tyler).** Code the argument whichever product it favors; target framing alone carries the brand-specific read. The dashboard must answer "what arguments do we lose to".
- **The taxonomy is discovered, never guessed (DECIDED 2026-09-22).** Discovery runs taxonomy-free on grok, embeddings-first consolidation proposes codes, the customer confirms at the gate. `getReasonTaxonomy` deleted.
- **Scope sentences travel with the code everywhere (DECIDED 2026-09-25).** The confirmed one-line definition goes into the labeler prompt, the training prompts and inference. Names alone under-specify the contract: the v3 relabel filed covered arguments as uncoded and the coder learned its keys, not its definitions; v4 labels with definitions fixed it. Unseen brands need the sentences at inference (~5 reason F1).
- **v4 definitions stay; v5 contract definitions rejected (DECIDED 2026-09-26).** v5's longer per-code definitions created cross-code overlaps (Netflix plan tiers 30% -> 8%) without shrinking the uncoded residue, and were no easier to learn (v5b). A definition checker must add a cross-code overlap check before it is used for real.
- **No taxonomy adds for v0.2 (B8, DECIDED 2026-09-27, Tyler).** The confirmed codebooks stay as confirmed; arguments no code covers stay in uncoded_reason. Residue is small and scattered: AmEx v0.2 labels 5.0% of answers carry an uncoded reason, largest cluster consumer credit-score impact ~1% (51 of 4,868), then airport-screening speed, retention offers, credit union membership, ATM rebates, plus off-category ecosystem-cell arguments; v4 labels jira 3.4% / Netflix 11.2% / Pixel 4.5% with every named cluster under 1% (Netflix home bandwidth ~24, Pixel return policy ~13). Nothing reaches discovery's 2% add floor. Rejected: hand-picked adds (bypass the customer gate; sub-1% codes have ~30-60 training rows per tracker), widening scope sentences (v5 showed rewording moves labels between neighbors - plan tiers 30% -> 8%), a written threshold rule (nothing passes today, so same outcome).
  - **R&D exploration (NOT committed to v0.2): the coder outputs uncoded_reason too.** v0.1 ignores the field. If the coder learns it, every prod wave collects its own residue, which can be clustered after the wave and surfaced at the codebook gate as proposed adds once a cluster passes the floor - the codebook-drift trigger planned for finalizeRun, and the long-term answer to B8. Labels already carry the field; the cost is a longer training target; the risk is the 9B filling it with noise, measurable only in a coder eval (not the labeler isolated tests). Tracked in AGENTS.md To do.
- **uncoded_reason** is a discovery valve only: reasons stay strictly on the confirmed list.
- **Taxonomy adds for the post-scope residue** (AmEx consumer credit-score impact, retention offers; Netflix home bandwidth; etc.): OPEN, Tyler's call. Any codebook change forces a reasons relabel.

## 4. Judgment rules (the codebook's judgment half)

- **Outcome (O-TEST):** could a reader who saw only this answer act now and buy one named product without first classifying themselves? yes -> pick; must self-classify -> conditional; declines to advise with no product direction -> clarification (rare); informs or lays out options while championing none, or recommends only actions -> no_pick.
- **Stated defaults (O-DEFAULT):** a default with exceptions or caveats after it is a pick and its default is the top pick; a #1 in an advice-ranking for the reader's scenario is a default; keep or renew what you have = pick. Two finalists as equals, branches with no default, shortlists to pilot -> conditional. Trailing questions and offers change nothing.
- **Framing by direction, not enthusiasm (F1-F6):** recommended only when the answer points this reader toward the brand (pick, default, best-for, top of an advice-ranking, strong-verb branch, keep/renew); praise without direction, market superlatives, weak-verb hedges and reported opinions are mentioned; negative when the answer itself criticizes or a caveat disqualifies the brand for this reader - a caveat inside a standing endorsement does not flip it.
- **Out-of-category picks:** DECIDED (B5, section 5) - labeling unchanged; handled in reporting.
- **Which questions the coder scores (DECIDED 2026-09-27, Tyler).** The coder was built for one job - when a buyer asks the AI to choose in the category, who wins and why - and the setup grid also carries settled-customer stages where that job doesn't exist. Split by stage (the cell declares it, like the doubt design):
  1. **Scored in full on the current coder** (outcome, top pick, framing, reasons, mentions, doubt verdict where the cell has one): buyer choice - discovery, shortlist, criteria, feature_screening, use_case, social_validation, comparison, alternatives, pricing, premium_worth; buyer doubt - objections, business_case; keep or leave - churn_triggers, renewal (scored as a choice - "keep/renew = pick" - with the doubt verdict; must name the brand, A3).
  2. **Current coder, visibility-only reporting:** problem_recognition (is the brand named before the buyer knows the category; how often the AI already points to products) and category_education (is the brand named; outcome is always no pick, so it is not reported).
  3. **Own taxonomy, own scorer (after v0.2):** problem_resolution, expansion, ecosystem, advocacy. Scored on whether the AI strengthens or weakens the customer relationship, plus a stage field: problem resolution - fixed within the brand / workaround / suggests switching; expansion - backs the growth plan or redirects; ecosystem - the brand's own companions vs other makers', rival intrusion; advocacy - strength of the case, reusing the doubt verdict and reason codes (both vary there: 45% rebuts / 36% confirms / 19% mixed on AmEx).
  - Evidence (AmEx v0.2 labels): problem_resolution is 100% no pick, 98% mentioned, 100% confirms - every field constant; ecosystem "picks" are companion apps (Expensify); renewal splits 44% recommended / 40% negative (the most varied stance signal); problem_recognition names AmEx in 33% of answers and 40% point to products.
  - **v0.2 consequences:** group 3 answers are left out of v0.2 training and evaluation (their current labels are constant or misleading); jira, Pixel and Netflix relabels skip them (~8% fewer answers); AmEx's existing group-3 labels stay on disk. The group-3 scorer is its own workstream after v0.2 (taxonomy draft, reference labels, scorer). Tyler's reasoning: Procerno is a buyer landscape tracker; settled-customer questions answer a different question (does AI keep and grow your customers).

## 5. v0.2 fields

- **Scope (DECIDED 2026-09-26, Tyler):** v0.2 labels and learns every field prod reads, so it can replace the grok pipeline and the separate Haiku focus call. - **Doubt verdict (DECIDED 2026-09-27, Tyler).** Why: an objection answer can confirm the weakness ("yes, Jira can and often does slow badly") while its advice keeps the brand (pick / recommended); nothing recorded that the AI agreed with the criticism. premise_verdict = confirms | rebuts | mixed | n/a, plus premise_quote. "Confirms" = the answer tells the buyer the concern is warranted, even with conditions, fixes, or while still recommending the brand. About a third of confirmations still recommend the brand.
  - **The doubt comes from the cell, not the labeler (DECIDED).** `labeling/v02_relabel/question_designs.json`: doubt stages (objections, churn_triggers, renewal, problem_resolution, premium_worth) plus advocacy prompts that quote a critic; the design line is prepended to the request; everything else is n/a by construction. Self-detection inferred premises the question never stated.
  - **Per-question design check (DECIDED):** prompts that do not voice their cell's design (21 of 410, mostly jira's "Jira Cloud trial" cell) get no design line.
  - **Loyalty "plan" verdict dropped (DECIDED):** backs 16/16 - the question presupposes the brand, so it never varied. Loyalty signal comes from existing fields (first-party vs third-party companions via the dictionary, rival leakage, reason codes in advocacy, the doubt verdict on advocacy prompts that quote a critic).
- **Off-design prompts' answers are left out of the v0.2 relabel (DECIDED 2026-09-27, Tyler).** `labeling/v02_relabel/off_design_prompts.json`; rewrite them before the next collection.
- **Known field gaps (OPEN, from the AmEx labels 2026-09-27):**
  - B2 - **DECIDED 2026-09-27 (Tyler), pending an isolated test:** a brand framed two ways in one answer (384 of 4,868 AmEx answers list AmEx more than once with different framings, e.g. Gold recommended, Platinum criticized). The single brand-level framing is replaced by two signals: **recommended** (any of the brand's products recommended) and **criticized** (any warned against); both can be true. Rejected: negative wins (prod's old merge rule - an answer that picks an AmEx card would read negative for AmEx), recommended wins (hides product criticism), a single brand-level framing with per-product detail (still needs one of those rules). Schema change: target_framing becomes two booleans at brand level; per-brand framing in the mentions list stays; the dashboard funnel shows recommended rate and criticized rate, which can overlap. For comparisons with v0.1, a single framing can be derived from the two signals. **Isolated test (flagged, NOT RUN):** only this change, on the 200-answer set (~$5): the signals match the mentions' per-brand framings; run-to-run stability is at least today's 98%; no other field moves beyond the rerun baseline; the both-true share is hand-checked. Run separately from the B1 dictionary test.
  - B3 - **DECIDED 2026-09-27 (Tyler), pending an isolated test:** `clarification_requested` (the dashboard's "Asks back" column; also in export, study summary and workbooks) was true on 52% of AmEx answers, almost all trailing offers. New definition: true only when the answer asks the reader for information it needs to give or refine its advice (budget, size, usage, situation); offers to do more ("want me to...", "would you like...") and rhetorical questions do not count. Same boolean, redefined - no schema change. Distinct from the "clarification" outcome (answer only asks, no product direction). Rejected: splitting into info-request + offer flags (the offer flag says little about brand visibility), keeping it as is, dropping it (dashboard/export read it). **Isolated test (flagged, NOT RUN):** only this change, on the 200-answer set (~$5): offers no longer fire, real information requests still do (hand-checked), the rate falls to the information-request share, no other field moves beyond the rerun baseline.
  - B4 - **DECIDED 2026-09-27 (Tyler), pending tests:** price and spec flags (dashboard "Prices" / "Specs"). They vary widely by engine on AmEx (prices 55% Sonar to 94% Gemini; specs 63% to 97%), so they carry signal; the problem was B2B-only examples leaving APRs, earn rates and non-price dollar figures ambiguous. New generic rule for every category: price = what the buyer pays (price, fee, subscription, interest rate); spec = what the product delivers in numbers (capacity, limits, earn rates, sizes, speeds); keep the "actual figure" test; examples from many categories. Rejected: keep as is, per-category definitions (per-tracker review, breaks cross-tracker comparison), a mechanical detector (can't tell a fee from a spend example). Overfitting guard: validated on the held-out categories (below), not only the isolated full-prompt test.
  - B5 - **DECIDED 2026-09-27 (Tyler): not a coding change.** Out-of-category picks (AmEx ecosystem answers "pick Expensify") keep today's labeling: outcome describes the answer's decisiveness whatever it recommends. Brand credit is already correct - a pick of an ignored or untracked name credits no brand, since only approved dictionary brands earn "chosen". **Reporting to-do:** a computed in-category flag (the top pick resolves to an approved brand in the confirmed dictionary) so the "AI makes a firm pick" rate can be shown for category picks only; outcome reporting split by stage (loyalty cells expect non-category picks) is a later dashboard call. **Future version idea:** code adjacent out-of-category brands (Expensify, Roku, Marketplace apps) as their own class and map their associations with tracked brands (which companions the AI pairs with which brands).
  - B7 - **DECIDED 2026-09-27 (Tyler), pending an isolated test:** per-brand role in the mentions list. Outcome is answer-level and the only per-brand judgment was framing, so "recommended" lumped the winner with everything listed (AmEx labels: 3.0 recommended brands per conditional answer, 2.3 per pick answer). Each mention's framing is replaced by one role, built as a split of "recommended" only so no existing boundary moves: **chosen** (the top pick - mechanical), **branch winner** (the product the answer names as the answer for a stated condition), **shortlisted** (recommended under today's framing rules, neither of the others), **mentioned** (unchanged), **warned against** (today's negative, renamed). Framing is derived: chosen + branch winner + shortlisted = recommended. With B1's dictionary entry on every mention, B2's two brand-level signals are computable from the roles (recommended = any of the brand's products chosen / branch winner / shortlisted; criticized = any warned against). Branch-winner rule: two products named for one branch are both shortlisted; nested conditions - the innermost stated winner; "also consider X" is shortlisted. Mechanical checks: chosen = top pick; exactly one chosen in a pick answer; branch winner only in conditional answers; conditional answers with no branch winner flagged. Why this shape: Tyler's concern was new boundary problems (branch winner, shortlisted vs mentioned, warned against); only branch winner vs shortlisted is a new call, and it is collapsible - if unstable, it merges into shortlisted with no relabel. Rejected: leave as is; role alongside framing (two overlapping labels per mention); adding a branch table (condition -> winner; heavier, later version). **Isolated test (flagged, NOT RUN):** only this change, on the 200-answer set (~$5, plus ~$5 for a second run to measure branch-winner stability): derived framing matches the baseline's per-mention framing within the rerun baseline; branch winner vs shortlisted is stable run to run (else collapse); the mechanical checks pass; no other field moves beyond the rerun baseline.
  - B6a - **DECIDED 2026-09-27 via B10 (Tyler):** the target is present when named in the answer OR discussed by clear reference ("the card", "the fee", "it") to a brand the question names, recorded with a by-reference marker. Why: 10 AmEx answers to branded doubt questions were marked absent while their doubt verdict said confirms. Blind prompts need the brand named in the answer, so blind visibility is unaffected. Rejected: named only (loses stance on branded doubts); named only and skip stance on branded prompts.
  - B6b - **DECIDED 2026-09-27 (Tyler):** the focus quote is the sentence that most directly states how the answer positions the brand (its verdict on it); the first such sentence breaks ties. Replaces the unspecified "one verbatim sentence about the brand".
  - B6c - **RESOLVED BY B1 (Tyler 2026-09-27):** top pick naming variants ("Gold" vs "Amex Gold"; 12 of 13 top-pick disagreements in the blind review). ## 10. Settled-customer codebook (group 3) - PROPOSED 2026-10-10

**Scope.** The four stages the stage contract (2026-10-03) marks "settled customer (scorer to build)": business_case (row 12), expansion (16), ecosystem (17), advocacy (18). This moves business_case out of the 2026-09-27 split's group 1 ("buyer doubt"), following the later contract: its asker already has the brand and its read is case strength, not a buyer's verdict. problem_resolution is not in this codebook - it left the grid on 2026-10-02 pending the evidence-grounded redesign; its legacy cells stay unscored. The stage comes from the cell (the request's design line), never from the labeler, exactly like the doubt design.

**Why a separate codebook.** The buyer-choice fields are constant or misleading here (AmEx v0.2 labels: ecosystem "picks" were companion apps; the asker already owns the brand, so O-TEST and target framing answer a question nobody asked). The client question is "does the AI keep and grow our customers": arm or concede, back or redirect, surround us with our own things or with rivals'.

**Fields (every group-3 answer).**
- `relationship_verdict`: strengthens | neutral | weakens - by DIRECTION, the F-rule logic transposed to a customer: more committed to the brand for what they asked, no position or balanced, less committed. A caution the question asked for never weakens by itself; a caveat inside a standing endorsement does not flip it.
- `redirect_to`: every brand the answer tells this customer to use INSTEAD of the brand (or instead of extending it) for the ask, as written. A companion recommended ALONGSIDE the brand is a pairing, not a redirect. Rival-or-not is resolved at read time from the confirmed dictionary (the B5 principle: the labeler records names, the dictionary decides category).
- `mentions` (brand + framing, the v0.2 wording verbatim) and `reasons` + `uncoded_reason` (brand-agnostic, the confirmed list with scope sentences) - the arguments the AI uses for and against us with our own customers. `quote`: the verbatim phrase deciding the verdict.
- Stage field, exactly one per row:
  - business_case `case_strength`: strong (builds the affirmative case; caveats minor) | hedged (qualifies it so materially the champion could not present it with confidence) | undermined (argues the case is weak or steers elsewhere).
  - expansion `growth_stance`: backs (supports the step with the brand; how-to guidance and execution cautions still back) | neutral | redirects (another product or a specialist for the step, or against the step).
  - ecosystem `pairings[]`: every product put forward for the ONE need, each with `maker_relation` own | third_party | substitute and `framing` recommended | mentioned | negative. The read is the share of recommended pairings that are own / partner / rival, with third_party split into partner vs rival at read time by the dictionary; a recommended substitute is also a redirect.
  - advocacy `case_strength`: strong (equips a confident case, rebuttals where a critic is quoted) | partial (points for the brand but concedes material ground or lands on "both are fine") | concedes. Plus `premise_verdict` / `premise_quote` on rows whose cell quotes a critic (the existing doubt design line rides along; n/a otherwise) - the Objections read, kept separate from case strength, per the contract.

**Reads this produces (dashboard, per tracker).** Business case: strong / hedged / undermined, redirect rate. Expansion: backs / neutral / redirects, redirect targets. **Contract-wording principles (Tyler 2026-10-27): rules state what governs, never a named feature - the record is now a standard.** Written after the frame test's two-direction failure, because the same failure shape has now been measured five times (decompose3 prompts, the Netflix confusion sentence, the v5 definitions, the journeys25 stakes field, frame rounds 1-2). The principles bind every future edit to model-facing text - labeling definitions, codebook scope sentences, coder prompts, writer rules, checker lines:

1. **Naming a feature raises its salience on every row, in both directions.** A sentence that names an ingredient (measure advice, a code pair, a prohibited phrasing) re-weighs the whole continuum, not the boundary cases: prohibition moved partial 82 -> 205, protection moved it 82 -> 40, on the same 650 answers. A wording edit is a threshold shift, never added discrimination.
2. **A proportion-or-subordination boundary cannot be stated as a feature rule.** When the distinction is which element is the answer's spine and which is decoration (what the advice is FOR), the levers are labeled examples - training rows, adjudicated anchors - or a separate labeled field. Never another definition sentence; the frame test's stop rule is the precedent.
3. **The definition IS the measurement, so every edit runs a pre-registered paired test**: an answer key of rows that must flip and rows that must not, control floors from rerun pairs on case-unchanged rows, coverage, and a stop rule. Two failed directions on one boundary means the lever is wrong, not the words - stop, no third round.
4. **Check leakage into fields the sentence never mentions.** Round 2's advocacy sentence moved relationship_verdict on 30 rows and pushed premise_verdict and the quotes below floor. Controls-at-floor is a gate, not a report line.
5. **Where the defect is countable, use a string reading, not a judgment line** (the seed-hardening and ss-series lesson: a judgment checker cannot tell implicit from absent, and a model follows a sentence in its most literal reading). Where it is not countable, see principle 2.
6. **Judge each rule on rows that did not inspire it, against the human's calls** - never against what the previous model served (the dictionary A4 convention; arm N's circularity is the counter-example).
